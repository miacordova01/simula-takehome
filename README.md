# Simula - CTR prediction and candidate ranking

A CTR model, a candidate ranker, cold-start handling, a drift adaptation layer,
and a serving path benchmarked at **1.5ms p99** against a 50ms budget.

```bash
brew install libomp                          # LightGBM needs it on macOS
export SIMULA_DATA_DIR=/path/to/csvs         # defaults to ~/Downloads
./run_all.sh                                 # ~15 min, regenerates everything
```

`run_all.sh` creates its own virtualenv and installs `requirements.txt`. It
needs `impressions.csv` and `characters.csv` in `SIMULA_DATA_DIR`.

**What's in this bundle:** source (`simula/`, `scripts/`) and the generated
analysis (`reports/`), so every claim below can be read without running
anything. Trained artifacts, the parquet cache and the virtualenv are omitted -
they're all regenerated by `run_all.sh`.

Once trained, `python scripts/demo.py` ranks a live slate for two contrasting
chat contexts in ~2s (no CSV load) - safety gating, cold-ad exploration, budget
pacing, frequency capping and a latency measurement, all with per-ad reasons.

## The headline

Before building anything I ran an out-of-time signal audit
([`reports/signal_audit.md`](reports/signal_audit.md)): for every column,
estimate a per-value CTR on days 21-27, score days 28-30 with it, and compare
against the same column shuffled. The gap between the two is the column's
usable signal, with the noise floor measured rather than assumed.

The result reshaped the whole project:

| Column group | Transfer AUC edge | Verdict |
|---|---|---|
| `site_id`, `site_domain` | 0.163, 0.146 | dominant |
| `C21`, `C14`, `C18`, `C17`, `app_id` | 0.104-0.114 | strong |
| `character_id` | 0.042 | real but modest |
| `safety_tier` | 0.012 | real, small, unconfounded |
| `conversation_turn` | **-0.002** | **no signal** |
| `session_msg_count` | **-0.000** | **no signal** |
| `session_progress` | **-0.000** | **no signal** |
| `creator_type` | **-0.001** | **no signal** |
| `char_age_days` | **-0.000** | **no signal** |

**The conversation-state features carry no information about clicks in this
dataset.** Not "weak" - indistinguishable from a shuffled control, and a
retrained ablation without them scores *marginally better* than with them. The
same is true of `creator_type`, character age, and (as a monotone effect)
`num_interactions`.

This matters because the brief leans on those columns, and the tempting move is
to build elaborate conversation features and report that the model works. It
does work - but the work is being done by the publisher surface and the creative
attributes, and saying otherwise would be dressing up noise.

Three things in the character layer *are* real:

- **`character_id` itself.** A variance decomposition separates true
  between-character spread from binomial noise: 48% of the observed spread is
  real, implying a true between-character CTR sd of 0.024 against a 0.185 base.
  Meaningful, and worth an encoding - but a fraction of what the raw per-character
  CTR table suggests.
- **`safety_tier`.** `mature` characters run at 20.2% CTR vs 17.6% for `sfw`.
  I checked for confounding by directly standardising over `C15`, `site_id`,
  `app_id` and `C18` strata; the lift is unchanged in all four (0.2018-0.2042).
  Cramer's V between tier and every context column is under 0.011, so characters
  are assigned to traffic essentially at random. This is a clean effect.
- **`character_description` text**, for cold start only - see below. That one
  surprised me.

Ablation confirms the sizing. Retraining the full model with one family removed:

| Removed | AUC delta | RIG delta (relative) |
|---|---|---|
| target encodings | -0.0693 | -56.2% |
| character features | -0.0070 | -6.6% |
| device features | -0.0051 | -4.9% |
| cross features | -0.0026 | -1.1% |
| count features | -0.0000 | -1.0% |
| **conversation state** | **+0.0010** | **-0.0%** |

Dropping conversation state is free - slightly positive on AUC, indistinguishable
on RIG. It contributes 0.8% of total split gain versus 8.5% for the character
features. I kept the columns in the pipeline anyway, because in a live Simula
deployment they plausibly *do* matter and the cost of carrying them is near zero;
but nothing in this dataset supports building on them.

## 1. CTR prediction

### The split

Strictly temporal - day 21 dropped (no history to encode against), days 22-27
train, day 28 validation, days 29-30 held out.

A random split would leak three separate ways here: the same `device_ip`
straddles both sides, target encodings would see future clicks, and the
character popularity mix would be identical across folds when in production it
emphatically is not - the top-200 character set has a Jaccard half-life of about
two days and only 14% of day 1's popular roster survives to day 10.

### Leakage-safe target encoding

Everything is high-cardinality categorical (547k `device_ip`s), so one-hot is
out and LightGBM's native categorical handling degrades past a few hundred
levels. Target encoding is the workhorse - but the standard K-fold OOF trick
still lets the encoder see the future.

Instead each day is encoded using **only days strictly before it**, which is
exactly what a nightly feature-store rebuild produces. No row is ever encoded
with a click that had not yet happened, so offline numbers transfer.

Unseen values back off hierarchically (character -> safety tier, site -> site
category) rather than to the global mean, and each encoded column carries a
`seen_*` flag so the trees can learn a separate response surface for the cold
path instead of having one hand-coded.

### Results - held-out days 29-30

| Model | AUC | PR-AUC | RIG | Calib ratio | ECE |
|---|---|---|---|---|---|
| Base rate | 0.500 | 0.171 | -0.002 | 1.085 | - |
| Hashed logistic regression (2^20) | 0.700 | 0.328 | 0.072 | 1.017 | 0.025 |
| **LightGBM + time-aware TE** | **0.710** | **0.341** | **0.091** | **1.005** | 0.014 |
|  + rolling isotonic | 0.708 | 0.337 | 0.087 | 0.953 | **0.013** |

LightGBM beats the hashed baseline by 22% relative RIG. The baseline is there
because every large ad system has one - it retrains in minutes and handles unseen
values by construction - and if the GBM couldn't clearly beat it, the extra
serving complexity wouldn't be worth it.

### Why these metrics

AUC is invariant to monotone rescaling, so a badly calibrated model can post a
great AUC and still lose money. Since `bid = pCTR x value`, a systematic 20%
overprediction spends 20% too much. So the headline is **normalized entropy /
RIG** (log loss against the base-rate predictor - the metric Facebook's ad
ranking papers optimise, because it penalises miscalibration directly), plus
calibration ratio and ECE, plus per-opportunity ranking metrics for the ranker,
plus everything sliced by cold-start status.

### A calibration result worth flagging

Fitting isotonic regression on the validation day - the textbook move - **made
calibration worse** (ECE 0.014 -> 0.018). The validation day ran at 16.5% CTR
against the test window's 17.1%, so the calibrator baked in yesterday's level and
systematically underpredicted.

Refitting isotonic on a rolling 12-hour window with a 2-hour attribution lag -
what an online recalibration job actually has available - improves ECE to 0.013
instead. Aggregate ratio degrades slightly (0.953 vs 1.005) because the window
lags a moving level, so the raw model is competitive; the useful conclusion is
that **a frozen calibrator is actively harmful when the base rate drifts**, and
recalibration has to be continuous.

### Known weakness

Cold sites (167 test rows) are genuinely broken: AUC 0.47, predicting 17% where
actual is 9.6%. The `site_category` backoff isn't enough because site is the
strongest feature in the model. Fix would be a stricter prior on unseen sites
plus a bid discount until they accumulate data - not implemented, and I'd rather
name it than bury it.

## 2. Candidate ranking

`simula/ranker.py`. Score:

```
score = pCTR_ucb x bid_cpc x pacing x fatigue x diversity
```

Ranking is not sorting by pCTR. Four things pull in different directions:

- **Expected value, not click probability.** A 2% CTR ad at $5 CPC beats a 6% ad
  at $1.
- **Uncertainty.** Sorting on point estimates means never learning. Scores carry
  a Beta-posterior UCB bonus that shrinks as ~1/sqrt(n), so a cold ad gets optimism
  that decays automatically - no "new ad" code path, no threshold. Thompson
  sampling is implemented as an alternative; UCB is the default because
  deterministic rankings are far easier to debug and to explain to an advertiser
  asking why they lost.
- **Hard constraints run before scoring.** A `mature` creative on an `sfw`
  character is a brand-safety incident, not a ranking mistake. A big enough pCTR
  must not be able to buy past it.
- **Cross-request state** (budget pacing, frequency caps) applies as smooth
  multipliers, not cliffs. A hard cutoff at budget exhaustion shows up as a CTR
  cliff at a fixed hour every day.

### Does it work?

Evaluated on **natural slates** - groups of held-out impressions sharing a
context key but differing in ad attributes, scored on real labels:

| Context key | Groups | group AUC | recall@1 | NDCG |
|---|---|---|---|---|
| site+app+character+hour | 1,851 | 0.552 | 0.514 | 0.807 |
| site+character+hour | 4,616 | 0.653 | 0.574 | 0.823 |
| app+character+hour | 7,897 | 0.692 | 0.606 | 0.832 |

Group AUC is below pooled AUC, which is correct and healthy: pooled AUC gets
free credit for separating a high-CTR surface from a low-CTR one, which the
ranker never has to do since the surface is fixed at request time. Reporting only
the pooled number would overstate the ranker's value.

**Caveat I'd raise before anyone acts on these:** natural slates here have median
size 1, because the logged system served one ad per opportunity. The tightest
context key (0.552) is the conservative read, the loosest (0.692) the optimistic
one. Getting this properly needs an interleaving or explore-bucket experiment,
not logged single-slot data.

### Is the ranker actually context-sensitive?

A model with no contextxad interaction produces the same ordering for every
request, making per-impression ranking theatre. So I tested it: one fixed set of
40 ads scored against 300 different contexts.

- Mean pairwise Spearman between orderings: **0.394** (not 1.0 - orderings
  genuinely move)
- **23 of 40** distinct ads win the top slot across contexts
- Same ad's pCTR varies **3.2x more** across contexts than average pCTR varies
  across ads

That last number is the honest one: context dominates ad choice. Most of the
model's value is in *pricing* the impression; a smaller but real slice is in
choosing between ads. It also points at where the next effort pays - richer
ad-side features, not richer context features.

Worked examples with safety gating, pacing and fatigue live in
[`reports/ranking.md`](reports/ranking.md) and
[`reports/sample_rankings.csv`](reports/sample_rankings.csv).

## 3. Cold start

**Sizing first.** On held-out data: cold `device_ip` is **61% of traffic**, cold
creative ids ~37%, cold `character_id` **0.9%**, and exactly 3 characters in the
catalogue were never served. "New user" is the dominant cold-start case by two
orders of magnitude. The brief's character cold-start question is real but small;
sizing it before solving it is most of the value.

**What carries signal with zero history on an entity?** On the cold-user slice,
`site_id` alone gives AUC 0.652, `app_id` 0.611, the creative attributes
0.53-0.60. User identity was never carrying much signal, which is why the
cold-device slice barely loses accuracy in the full model.

**Bootstrapping a new character** - and here I was wrong. I expected persona text
to be decorative. Holding out 20% of characters entirely and predicting their
CTR:

| Method | Corr with actual | MSE |
|---|---|---|
| Global prior | - | 0.0028 |
| `safety_tier` backoff | 0.261 | 0.0026 |
| **`character_description` TF-IDF + ridge** | **0.477** | **0.0023** |

The description text nearly doubles the correlation over tier backoff. A content
tower for character cold start is worth shipping - the one place in this dataset
where the character layer earns real modelling effort.

**Graduation, measured not guessed.** Bucket characters by training-window
impressions, then compare two predictors of their *test* CTR: own smoothed
history vs tier prior. With no shrinkage, own history first wins at **~400
impressions**. With shrinkage the penalty for being early nearly vanishes.

Conclusion: **don't build a discrete cold-start path with a graduation event.**
A shrunk estimator plus a UCB bonus gives a continuous handoff, removes the
threshold as a tuning parameter, and avoids a discontinuity in serving behaviour.

## 4. Drift

### Measured

- **Target moves.** Daily CTR swings 16.5%-19.6%, an 18% relative range with |z|
  up to 15 - far beyond sampling noise.
- **Character churn is the fastest-moving thing in the data.** Top-200 Jaccard
  half-life ~ 2 days; consecutive days overlap ~0.7, so a third of the popular
  roster turns over daily. Any per-character statistic estimated on a week is
  describing a cohort that no longer exists.
- **PSI vs day 1**: `character_id` and the creative ids drift hardest;
  `banner_pos`, `safety_tier`, `conversation_turn` barely move. That tells you
  what to re-estimate often and what to cache for days.

### The bug this caught

The first staleness curve showed calibration exploding to 2.18 and RIG going
negative on day 27 - a cliff, not a decay. **That was not drift.** `day_of_week`
was a numeric ordinal, the training window covered only Wed-Fri (dow 2-4), and
day 27 is the log's single Monday (dow 0). Every row fell off the left end of the
trees' split range.

Dropping the feature - it's also unidentifiable on 10 days, where each weekday
occurs once or twice and is perfectly confounded with that date's traffic mix -
turned the cliff into a smooth decay and improved the main model too (AUC
0.708->0.710). `scripts/debug_staleness.py` isolates it.

The general lesson: **a sudden metric cliff in a temporal backtest is far more
often a feature-encoding bug than a real regime change**, and "looks like drift"
is an expensive way to be wrong.

### The second surprise

Refreshing target encodings under a frozen tree ensemble *improves AUC* (+0.001
mean) but *degrades calibration badly* (ratio 1.01 -> 1.16, RIG down every day).
A frozen ensemble's leaf values were fitted against the encoder distribution at
training time; swap fresher encodings underneath and you get a better ranker
emitting worse probabilities.

So: **refreshing the feature store under a frozen model is not safe on its own.**
It must be paired with a recalibration pass. Hourly calibrator refit, hourly
encoding refresh (only together), daily tree retrain.

### The adaptation layer

`simula/adaptive.py` - time-decayed Beta posteriors per arm (48h half-life).
Decay does three things a cumulative counter can't: tracks drift, re-inflates
uncertainty on arms not served recently so novelty recovers automatically, and
bounds memory to one float pair per arm.

Evaluated by inventory-constrained replay over the held-out days, with the slot
budget set to 50% of logged volume so the policy actually has a choice:

| Policy | CTR | vs logged | Top-10 ad share | Cohort ad entropy |
|---|---|---|---|---|
| logged (status quo) | 0.1675 | - | 37.7% | 4.046 |
| static greedy | 0.2229 | +33.0% | 46.3% | 3.941 |
| decayed Thompson | 0.2243 | +33.9% | 45.2% | 3.978 |
| **decayed Thompson + fatigue** | **0.1999** | **+19.3%** | **21.1%** | **4.705** |

The unconstrained bandit buys its +34% by concentrating harder - higher CTR
through less variety, which is exactly what causes fatigue. **The fatigue-damped
policy dominates the status quo on both axes**: CTR +19.3% *and* top-10 exposure
share cut by 44%. That's the trade the brief asks for. The ~14 points of CTR lift
given up versus the greedy bandit is the explicit price of diversity - a choice,
not a hidden loss.

One caveat on the knob: it's monotone but **not smooth**. Almost the entire
effect lands between 0.0 and 0.2 and then saturates, because the damping is
`1/(1 + k*exposure)` - once `k*exposure` exceeds 1 for the heavy arms, raising
`k` rescales them together without changing the ordering. It's a switch with a
short ramp, not a dial. A production version would express it as a repetition
target ("no user sees a creative more than 3x/day") and solve for `k`.

**Replay assumption, stated plainly:** within a (cohort, ad-group, hour) cell,
logged impressions are treated as exchangeable. That holds unusually well here
because character assignment is independent of the ad columns (Cramer's V <
0.011) - which is precisely the condition this estimator needs.

## 5. Productionization

Measured on the real scoring path ([`reports/latency.md`](reports/latency.md)),
not asserted:

| Slate size | p50 | p95 | **p99** |
|---|---|---|---|
| 10 | 0.42ms | 0.52ms | 0.60ms |
| 50 | 1.27ms | 1.44ms | **1.54ms** |
| 100 | 2.33ms | 2.56ms | 2.65ms |

**p99 = 1.5ms at 50 candidates** - full path including safety gate, UCB, pacing,
fatigue and sort. That leaves ~48ms for network, retrieval, auction and logging.
~786 req/s single-core; ~7,500 on a 16-core box at 60% utilisation.

(Measured on an M-series Mac; absolute numbers move a little run to run with
machine load, but the headroom against a 50ms budget is ~30x either way.)

Three design choices got it there:

1. **Context/ad split.** Every feature is context-only, ad-only, or a cross.
   Context features are computed once per request and broadcast down the slate.
   Worth a measured **2.0x** at 50 candidates, widening linearly with slate size.
2. **Dicts, not pandas.** Encoders convert from Series to plain dicts at load.
   A `dict.get` is ~40ns; a `Series.map` on 50 rows is ~50us of pure overhead.
3. **One batched predict.** N candidates as a single (N, F) float32 array.

### Architecture

```
request --> Feature assembly --> LightGBM --> Ranker --> auction
              |                    (94 trees)   |
              +-- context cache (per session)   +-- safety gate  [hard]
              +-- TE tables (in-process, RO)    +-- UCB bonus
              +-- candidate features (in-proc)  +-- pacing  <- Redis, 1s TTL
                                                +-- fatigue <- Redis, per-user
                                                +-- diversity

offline:  nightly retrain --> model.txt + encoders.pkl --> rolling deploy
          hourly    --> TE refresh + calibrator refit (together, never apart)
          streaming --> decayed Beta posteriors per arm
```

**Cache / precompute / approximate:**

- **Precompute:** TE and count tables, rebuilt hourly, shipped as a read-only
  in-process artifact (37MB here). No network hop on the hot path - a Redis
  round-trip per feature would blow the budget on its own.
- **Cache:** the context vector per session (conversation state changes, but
  site/app/device/character don't within a session). Character metadata is
  5k rows - keep it resident.
- **Approximate:** cap the slate at ~50 after retrieval; `device_ip` encodings
  can be sketched rather than stored exactly at 547k keys and growing.
- **Shed load:** if p99 breaches, fall back to the hashed logistic model (already
  built, 0.700 AUC vs 0.710) rather than dropping the request.
- **Mutable state in Redis** with short TTLs: pacing counters (1s staleness is
  fine), per-user frequency caps. Both degrade to "no throttle" on a Redis miss,
  which fails open rather than dropping ads.

## What I'd do next

**Data I'd want.** Click timestamps (for attribution lag and dwell-time
modelling), actual advertiser/campaign ids instead of anonymized C-features,
bid prices to optimise revenue rather than CTR, conversation *text* or an
embedding - the brief's premise is that mid-roleplay context matters, and the
turn-index columns can't test that, but message embeddings could. Also
post-click outcomes; CTR is a proxy and optimising it alone selects for clickbait.

**Models.** A two-tower retrieval model so the candidate set isn't given;
field-aware factorisation or a DeepFM-style cross layer for explicit adxcontext
interaction (the 2.8x context/ad asymmetry says that's where headroom is); a
proper multi-task head for click *and* conversion.

**Evaluation.** Everything here is offline replay. The next real step is an
interleaving experiment for ranking quality and a small explore bucket to get
unbiased counterfactual data - the group-AUC numbers above are the weakest
measurement in this repo and they can't be fixed with more logged data.

**Engineering.** Feature-store parity tests between `features.py` and
`serving.py` (they're mirrors today and will drift apart); calibration and PSI
monitors wired to alerts; shadow-scoring the new model against live traffic
before promotion.
